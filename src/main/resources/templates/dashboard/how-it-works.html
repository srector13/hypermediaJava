How it works

The browser asks for HTML, the server sends HTML. htmx adds a few attributes that let any element make a request and swap the response into the page. Everything a Vue/React SPA would keep in a client-side store stays on the server, in the URL, or in the DOM.

One interaction, end to end: typing in the search box

  • You type; htmx waits 300 ms of quiet
    input changed delay:300ms
  • GET /jdbc/employees?q=ana&sort=…
    HX-Request: true
  • Controller runs JDBC/JPA query
    store.search(query)
  • Thymeleaf renders the table fragment + inspector (OOB)
    FragmentsRendering
  • htmx swaps it in and updates the URL
    hx-push-url="true"

What you don't write

  • A JSON API, DTOs, and their OpenAPI/TypeScript twins
  • A client-side router, store, and the code that keeps them in sync with the server
  • Validation rules twice (client + server)
  • A bundler, transpiler, dev server, node_modules at runtime
  • Hydration, loading and error state for every fetch
  • Authorization checks in two places

What you do write

  • Controllers that return views or fragments (FragmentsRendering for several at once)
  • Thymeleaf templates, split into fragments the server can render on their own
  • Attributes: hx-get, hx-trigger, hx-target, hx-swap
  • A few lines of CSS for transitions (row flash, fade-out, toasts)
  • An SSE hub (~150 lines) if you want real-time
💡
Where an SPA still wins: heavily client-side interactions with no server round-trip, such as drawing canvases, offline-first apps, or complex drag-and-drop editors. For CRUD, dashboards, admin tools and line-of-business apps (most enterprise Java front ends), hypermedia covers the same ground with far less code. You can also mix the two: drop a small Alpine.js or Vue island into a page where it pays off.
